# AI 分身 IM 系统设计方案(完整版)

面向长期演进的架构设计:人与 AI 分身同处一个聊天应用,支持手动档/自动档,并为多分身协作、工具生态、企业化预留扩展点。

> 实现现状、落地取舍与端云/UI 细节分别见 [README](../README.md)、[design-essence.md](design-essence.md)、[client-cloud.md](client-cloud.md)、[ui-guidelines.md](ui-guidelines.md)。

## 1. 目标与设计原则

**产品目标**

- 每个用户拥有一个代表自己的 AI 分身,分身是会话中的一等成员。
- 用户可按会话、联系人、时间段设置「手动 / 半自动 / 自动」档位。
- 自动档下分身能代替回复并执行任务;手动档下仅在被 @ 时工作。
- 人与 AI 在同一套消息、会话、通知体系内,体验一致。

**架构原则**

1. **AI 旁路,不侵入主链路**:IM 核心不依赖 AI,AI 故障不影响正常聊天。
2. **分身即成员**:复用成员、权限、已读、@、撤回等全部 IM 能力,不另起一套。
3. **默认不信任**:他人消息一律视为数据而非指令;分身权限不超过主人。
4. **一切可审计、可撤回、可接管**。
5. **契约先行、插件化**:消息类型、工具、模型、策略、记忆均通过注册表和接口扩展,不改核心代码。
6. **事件驱动**:所有状态变化都是事件,新能力以订阅者形式接入。

## 2. 核心概念模型

| 概念             | 说明                                                                       |
| ---------------- | -------------------------------------------------------------------------- |
| Principal(主体)  | 能发消息、被授权的实体:human、avatar、bot、service、system                 |
| User             | 真人账号,拥有 0..N 个 Avatar(首期 1 个,模型上允许多个,如工作分身/生活分身) |
| Avatar           | 代表用户的 AI 主体,有人设、记忆、策略、工具授权                            |
| Bot / Agent      | 非个人的 AI 成员(群助手、客服、翻译),由群或组织拥有                        |
| Policy           | 描述「什么情况下,谁的分身,可以做什么」的规则                               |
| Capability       | 分身可调用的能力(工具),带风险等级和权限范围                                |
| Task             | 一次由消息或事件触发的 Agent 执行,有状态机和审计                           |
| Delegation(委托) | 主人对分身的授权凭证,限定范围、期限、额度,可撤销                           |

关键设计:消息的发送者和**代表者**分离——`sender` 是分身,`on_behalf_of` 是主人。这使「分身代发」「秘书式代理」「企业机器人」共用同一模型。

## 3. 总体架构

```
客户端 (iOS / Android / Web / Desktop / 小程序)
        │  WebSocket / HTTP / 推送
接入层:网关、鉴权、长连接、限流、多端同步
        │
IM 核心域:会话 · 消息 · 成员 · 已读 · 通知 · 文件 · 搜索
        │  事件总线 (Kafka / Pulsar)
┌───────┴──────────────────────────────────────────┐
│ AI 平台层                                          │
│  触发路由 → 策略引擎 → 任务编排 → Agent Runtime     │
│     │            │          │         │            │
│  语境服务    风险/审批   工作流引擎   模型网关        │
│  记忆服务    合规过滤    工具网关(MCP)  评估/护栏     │
└──────────────────────────────────────────────────┘
        │
开放平台:插件/工具市场 · Webhook · SDK · 第三方 Agent 接入
治理层:审计 · 观测 · 计费 · 配置中心 · 灰度/特性开关
```

**分层职责**

- **IM 核心域**:只关心消息可靠投递,对 AI 无感知,仅多了 `sender_type` 和 `on_behalf_of` 字段。
- **AI 平台层**:无状态服务集群,通过订阅事件工作,可水平扩展、独立发布。
- **开放平台层**:对外暴露稳定接口,第三方可接入工具、模型、Agent。

## 4. 档位与策略引擎

### 4.1 档位定义

| 档位        | 触发                      | 行为                                |
| ----------- | ------------------------- | ----------------------------------- |
| 手动 manual | 被 @(含主人 @ 自己的分身) | 仅响应被 @ 的请求                   |
| 草稿 draft  | 相关消息到达              | 生成回复草稿,主人确认后发送         |
| 自动 auto   | 与主人相关的消息          | 自主判断:回复、执行、转交主人或忽略 |
| 静默 off    | 无                        | 分身完全不工作                      |

档位只是策略的「预设」,底层是通用策略引擎,后续可扩展出更多档位而无需改代码。

### 4.2 策略模型(规则 + 作用域)

策略以声明式规则存储,按作用域合并,优先级从高到低:**会话 > 联系人/分组 > 场景标签 > 时间日程 > 全局默认**。示例:

```
policy:
  scope: {type: contact_group, id: family}
  mode: auto
  schedule: workdays 19:00-08:00
  allow_capabilities: [calendar.read, calendar.create, reply.text]
  deny_topics: [money, health]
  max_risk: L1
  rate_limit: 20 msgs/hour
  escalate_when: [confidence<0.7, sentiment=angry, mention_amount]
```

**扩展点**:条件(condition)由「条件插件」注册,如地理位置、日历忙闲、手机勿扰状态、会议中、驾驶中,新增条件只需注册一个求值器。

### 4.3 让位与接管

- 主人在线且正在输入:分身暂停。
- 主人手动回复后,该话题冷却 N 分钟(话题由语义聚类或回复链判定)。
- 主人一键「接管」,分身立即停止并交出上下文。
- 主人长时间无响应且对方多次追问:升级策略(提示对方「主人暂不在,已记录」)。

### 4.4 决策流水线

1. 事件进入触发路由,找出可能受影响的分身。
2. 策略引擎求值:档位、时间、范围、频率。
3. 小模型做意图分类:是否需要回应、紧急度、类型(闲聊/问答/任务/通知)。
4. Agent 规划:检索记忆与上下文,选择回复、工具调用或转交。
5. 风险评估与确认。
6. 执行、发消息、写审计、更新记忆。

每一步输出结构化结果(决策 + 理由 + 置信度),保存在任务记录中,便于回放和调试。

## 5. 消息与协议设计

### 5.1 消息结构(可扩展)

```
message:
  msg_id, conv_id, seq
  sender: {id, type: human|avatar|bot|system}
  on_behalf_of: user_id | null
  content: {type: text|image|file|card|task|form|custom, payload, schema_version}
  mentions: [principal_id]
  reply_to, thread_id
  ai_meta: {task_id, mode, tools_used, risk, confidence, hop_count, visibility}
  ext: {}   # 任意扩展字段,命名空间隔离
```

**扩展性要点**

- `content.type` 通过注册表扩展:新增卡片、投票、审批、代码块、日程卡等,客户端按类型渲染,不认识的类型降级为文本。
- `schema_version` 保证向前兼容;`ext` 用命名空间(如 vendor.xxx)避免冲突。
- `ai_meta.visibility` 控制 AI 过程是否对会话可见:仅主人可见 / 会话可见 / 隐藏。

### 5.2 AI 专用交互消息

- **确认卡片**:L2 操作请主人批准(同意/修改/拒绝),可带过期时间。
- **任务卡片**:长任务展示进度、中间产物、可取消。
- **草稿卡片**:半自动档的待发送内容。
- **解释卡片**:展开查看「为什么这么回、用了什么工具、引用了哪些记忆」。

### 5.3 事件总线主题

`message.created`、`message.recalled`、`member.changed`、`policy.changed`、`task.created`、`task.step`、`task.completed`、`approval.requested`、`approval.resolved`、`feedback.submitted`、`presence.changed`。所有新功能通过订阅这些事件接入。

## 6. 数据模型

**身份与关系**

- `principal`(id, type, owner\_id, status)
- `user`、`avatar`(id, owner\_id, persona, style\_profile\_ref, model\_profile, status, version)
- `delegation`(avatar\_id, grantor, scopes, expires\_at, revoked\_at)
- `contact`(user\_id, peer\_id, group\_tags, trust\_level)

**会话与消息**

- `conversation`(id, type, settings, ai\_settings)
- `member`(conv\_id, principal\_id, role, joined\_at)
- `message`(见 5.1,分库分表按 conv\_id,按 seq 有序)
- `message_edit`、`message_recall` 记录

**策略与能力**

- `policy`(id, owner\_id, scope\_type, scope\_id, rule\_json, priority, version, enabled)
- `capability`(id, name, schema, risk\_level, provider, version)
- `capability_grant`(avatar\_id, capability\_id, constraints)

**任务与审计**

- `agent_task`(id, avatar\_id, trigger\_ref, status, plan, steps, cost, trace\_id)
- `task_step`(task\_id, type, input, output, latency, model, tokens)
- `approval`(id, task\_id, requester, approver, payload, status, expires\_at)
- `audit_log`(append-only,含哈希链,防篡改)

**记忆与知识**

- `memory_item`(avatar\_id, scope\[contact/global\], type, content, embedding, source\_msg, sensitivity, ttl, confidence)
- `style_profile`(avatar\_id, features, examples)
- `knowledge_source`(avatar\_id, type, uri, acl)

**反馈与评估**

- `feedback`(msg\_id, actor, type\[accept/edit/reject/recall\], diff, reason)

所有表带 `tenant_id`,首期单租户,后期无需改表即可支持企业多租户。

## 7. Agent 运行时

### 7.1 组成

- **模型网关**:统一封装多模型(分类用小模型,规划生成用大模型),支持路由、降级、重试、限流、成本核算,换模型不改业务代码。
- **提示词装配器**:分层拼装——系统规则、人设、风格、策略约束、记忆、会话上下文、工具定义;各层可独立版本管理和灰度。
- **规划器**:ReAct / 计划-执行混合模式;简单回复走单步,复杂任务生成多步计划。
- **工具执行器**:参数校验、权限检查、沙箱、超时、幂等、重试。
- **护栏**:输入过滤(注入检测)、输出过滤(隐私、敏感、违规)、一致性检查(是否符合人设与主人意图)。

### 7.2 任务状态机

`created → planning → [waiting_approval] → running → [waiting_user_input] → completed | failed | cancelled | handed_over`

长任务持久化到工作流引擎(Temporal 类),支持中断恢复、人工介入、超时升级。

### 7.3 执行模式

- **同步快回**:秒级轻量回复,走低延迟路径。
- **异步任务**:订机票、整理资料、跨系统操作,先回「收到,处理中」,完成后回报。
- **定时/事件触发**:不仅由消息触发,也可由日历、邮件、Webhook、定时器触发(分身主动提醒、日报)。

## 8. 能力(工具)体系

### 8.1 统一能力接口

每个能力声明:名称、描述、入参/出参 Schema、风险等级、所需授权、是否幂等、是否可回滚、成本估计。采用 MCP 协议,第三方能力无需改动核心即可注册。

### 8.2 风险分级

| 级别         | 示例                             | 自动档处理     |
| ------------ | -------------------------------- | -------------- |
| L0 只读/对话 | 查日程、总结、回答               | 直接执行       |
| L1 低风险写  | 建日程、改自己的草稿             | 执行并事后通知 |
| L2 高风险    | 转账、删除、对外承诺、发布       | 必须主人确认   |
| L3 禁止      | 修改安全设置、授权他人、绕过确认 | 永不自动       |

风险可由**上下文动态升降**:同一动作对陌生人发起风险更高;金额、对象、时间窗口也会影响等级。

### 8.3 能力生态

- **内置能力**:日历、待办、联系人、文档、搜索、翻译、总结。
- **连接器**:邮件、云盘、协同办公、CRM、代码仓库、智能家居。
- **用户自定义能力**:无代码的「快捷指令」(触发条件 + 步骤),或 Webhook 接入自有系统。
- **能力市场**:审核、签名、版本、权限声明、用户一键授权,按能力收费分成。

### 8.4 授权方式

采用 OAuth 式委托:用户授权分身访问某服务,令牌由凭证保险库保管,分身运行时只拿到短期、范围受限的令牌,不接触明文密钥。

## 9. 记忆与个性化

### 9.1 记忆分层

- **工作记忆**:当前会话上下文窗口,滑动摘要。
- **情景记忆**:发生过的事件和承诺(「周四答应给张三报价」)。
- **语义记忆**:稳定事实与偏好(家庭、职位、饮食习惯)。
- **关系记忆**:与每个联系人的沟通风格、亲疏、禁忌话题。
- **程序记忆**:主人处理某类事情的习惯做法,可沉淀为可复用流程。

### 9.2 记忆治理

- 每条记忆有来源、敏感级别、置信度、过期时间。
- 检索时按**对话对象**做访问控制:对 A 说话时,不可使用只属于与 B 私聊的记忆。
- 主人可查看、编辑、删除记忆,支持「忘记这件事」。
- 敏感类记忆(健康、财务、证件)默认不可在对外对话中使用。

### 9.3 风格画像与学习

- 从历史消息提炼语气、长度、口头禅、表情习惯,形成风格向量与少量示例。
- 反馈闭环:主人采纳/修改/撤回都是训练信号,先用于调整提示词与偏好库,规模化后可做个性化微调(LoRA 类),并支持用户随时重置。
- 分身「成长」可视化:告诉主人它学到了什么,增强可控感。

## 10. 安全、隐私与合规

**威胁与对策**

| 威胁                          | 对策                                                                          |
| ----------------------------- | ----------------------------------------------------------------------------- |
| Prompt 注入(对方消息诱导越权) | 他人内容标记为不可信数据;指令通道仅来自主人与策略;工具参数校验;高风险二次确认 |
| 数据泄露(跨联系人泄露)        | 记忆与上下文按对象隔离;输出前隐私审查;敏感字段脱敏                            |
| 身份冒充                      | 分身消息强制标识;主人账号被盗时可一键冻结分身                                 |
| AI 互聊死循环                 | hop\_count 上限、会话限速、意图去重、重复检测                                 |
| 越权工具调用                  | 能力白名单、短期令牌、沙箱、审计                                              |
| 成本滥用                      | 每分身配额、预算上限、异常检测                                                |
| 模型幻觉造成承诺              | 不确定即转人;对外承诺类一律 L2                                                |

**透明与合规**

- 对方始终能看到「AI 分身代发」,并可选择「我只想和本人沟通」(请求转人工)。
- 数据最小化、加密存储与传输、可选端到端加密(此时 AI 在端侧或可信执行环境内处理,作为远期方向)。
- 数据主权:按地区部署、保留期限、导出与删除权。
- 企业场景:DLP、内容审计、留痕、法务保全、分级权限。
- 未成年人保护、AI 内容标识等法规要求纳入合规清单。

## 11. 多分身协作与 AI 间协议

- **分身对分身**:A 的分身与 B 的分身可直接协商(约时间、询价),双方主人收到结果摘要。需要在会话中明确标识,并有轮数上限与人工旁观开关。
- **群聊多分身**:同一群里多个分身同时在场时,需要**仲裁机制**:同一话题只允许一个分身代表其主人发言;被 @ 的优先;其余旁听并可私下告知主人。
- **分身内多 Agent**:一个分身背后可由专家 Agent 组成(日程专家、写作专家、检索专家),由主 Agent 调度,对外仍是一个身份。
- **开放 Agent 接入**:定义标准 Agent 接入协议(身份、能力声明、消息格式、授权),第三方 Agent 可作为 bot 加入会话,与分身通过统一接口交互。
- **跨应用互通**:预留与其他 IM/协同平台的网关,分身可代表用户在外部渠道收发消息。

## 12. 客户端体验设计

- **会话内**:AI 消息淡色气泡 + 「AI 代发」角标;点击展开解释卡片;长按可撤回/纠正/教它。
- **档位开关**:会话顶部一键切换,支持「本次对话自动 2 小时」这类临时模式。
- **@ 交互**:输入 @ 可选择自己的分身或他人分身(对方允许时);对分身下达任务时支持语音。
- **分身控制台**:
  - 档位与策略可视化编辑(模板:上班模式、会议中、休假、睡眠)
  - 能力授权管理
  - 记忆管理、风格预览(输入一句话看分身会怎么回)
  - 用量与花费
- **待办与确认中心**:L2 审批、进行中任务、转交给我的消息,聚合在一个入口,支持锁屏快速审批。
- **分身日报/周报**:替你回复了谁、做了什么、有哪些待你决定。
- **新手引导**:先从手动档开始,系统基于数据建议是否开启自动档,逐步放权。
- **无障碍与多端**:多端同步分身状态;离线时客户端仍可显示草稿与审批。

## 13. 可扩展性设计清单

| 扩展方向        | 机制                                                  |
| --------------- | ----------------------------------------------------- |
| 新消息类型      | 内容类型注册表 + 客户端渲染器 + 降级策略              |
| 新工具/能力     | MCP 注册、Schema 声明、风险等级、授权流               |
| 新模型/供应商   | 模型网关适配器,按任务类型路由,支持私有化模型          |
| 新档位/规则条件 | 策略 DSL + 条件插件,无需发版                          |
| 新触发源        | 事件适配器:邮件、日历、Webhook、IoT、定时             |
| 新记忆类型/存储 | 记忆接口抽象,向量库可替换                             |
| 新渠道          | 通道适配层(微信/邮件/短信/其他 IM)                    |
| 多租户/企业版   | tenant\_id、组织策略层叠加个人策略、管理后台          |
| 多语言/多地区   | 国际化、区域部署、本地合规配置                        |
| 多模态          | 内容类型含语音、图片、视频;模型网关支持多模态输入输出 |
| 端侧智能        | 小模型端侧运行隐私敏感任务,云端处理复杂任务           |

**工程层面**

- 服务以接口和事件解耦,AI 平台各模块可独立替换(例如把规划器换成新方案)。
- 全面使用特性开关与灰度,新策略/新提示词可按用户分层上线、一键回滚。
- API 与事件模式严格版本化,保证兼容。
- 提示词、策略、能力定义都当作可版本化的「配置即代码」资产管理。

## 14. 非功能性设计

**性能**

- IM 主链路不经过 AI,保持毫秒级投递。
- 分身快回目标:分类 < 300ms、简单回复 < 3s;复杂任务异步化。
- 小模型预过滤 + 规则快速丢弃,避免每条消息都调用大模型(成本关键)。
- 触发路由做分身粒度的批处理和去抖:连续多条消息合并为一次处理。

**可靠性**

- 事件至少一次投递 + 幂等消费(以 msg\_id + avatar\_id 去重)。
- AI 平台不可用时降级为纯 IM;自动档分身静默并提示主人。
- 工具调用幂等键、补偿事务,失败可重试或转人工。

**成本**

- 分层模型、缓存(相似问题、摘要复用)、上下文压缩。
- 每分身预算与速率限制,超额自动降级为手动档。
- 成本归因到任务、能力、用户,支撑计费与优化。

**可观测性**

- `trace_id` 贯穿消息 → 事件 → 任务 → 工具调用。
- 指标:触发率、自动回复占比、采纳率、撤回率、转人工率、延迟、成本、安全拦截数。
- 任务回放:完整还原每步输入输出,便于排查与合规。

## 15. 质量评估与持续改进

- **离线评测集**:覆盖闲聊、任务、注入攻击、隐私泄露、情绪场景,每次改提示词/模型必须回归。
- **线上指标**:采纳率(草稿被直接发送的比例)、撤回率、投诉率、对方满意度。
- **红队测试**:专门模拟社工、越狱、互聊死循环。
- **影子模式**:新策略/模型先在旁路运行(只生成不发送),与真实人工回复对比后再放量。
- **人工反馈入口**:每条 AI 消息可「点赞/纠正/举报」,数据回流记忆与评测集。

## 20. 技术路线决策

| 路线                      | 特点                                                                                       | 结论                                  |
| ------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------- |
| 全托管云(Cloudflare 类)   | Workers + Durable Objects + D1 + Queues,零运维、上线最快                                   | 适合验证期;DO 语义难迁移,存在厂商锁定 |
| 自建 + Go 全家桶          | 生态成熟、招人容易,但依赖多(Kafka、Temporal、etcd、Redis 等)                               | 可行,运维成本高                       |
| 自建 + Rust 全家桶        | 性能与内存安全好,部分组件成熟度不足                                                        | 范围应收窄,不宜全面采用               |
| Go 精简版                 | Go 模块化单体 + PostgreSQL                                                                 | 简洁可靠                              |
| Bun 全栈                  | TypeScript 全栈,迭代最快;单线程,生产成熟度需验证                                           | 适合 AI 层                            |
| **Rust 核心 + Bun AI 层** | 核心写路径稳定高效,AI 层快速迭代,PostgreSQL 为事实来源、Redis 为加速层(仅这两个有状态依赖) | **最终采用**                          |

**决策原则**

1. **依赖最少**:保留 PostgreSQL 与 Redis 两个有状态依赖:PostgreSQL 是唯一事实来源,Redis 只承担缓存、在线路由、跨节点广播、限流与临时状态;队列、搜索、向量先用 PG 的能力,出现瓶颈信号再引入专用组件。
2. **按风险划分语言**:凡是「出错会丢消息、乱序、断连」的归 Rust;凡是「需频繁改规则、接工具、调提示词」的归 Bun/TS。
3. **接口先行**:存储、队列、缓存、对象存储、模型、沙箱全部走接口,保证云方案、自建方案、精简方案可互换。
4. **AI 旁路**:AI 平台故障不得影响聊天收发。

## 23. 边界约定

1. **单写者**:消息表只由 Rust 写入。分身发消息必须调用 Rust 的 `SendMessage` 内部接口,sender 为 avatar 主体、`on_behalf_of` 为主人,seq 与一致性不被破坏。
2. **事件通道**:Rust 在同一事务内写「消息 + outbox」,Bun Worker 用 `FOR UPDATE SKIP LOCKED` 消费;AI 链路完全异步。
3. **Schema 所有权**:消息、会话、成员、已读、推送设备表归 Rust;策略、任务、记忆、审计、能力、审批表归 Bun。通过 PG 角色限制:Bun 对消息相关表只读,Rust 对 AI 表只读,互不越界写。
4. **契约单一来源**:proto 是唯一真相,用 buf 同时生成 Rust(tonic/prost)与 TS(connect-es)代码;CI 做破坏性变更检查,约定「只加不改」。
5. **追踪贯通**:`trace_id` 随消息、事件、gRPC 元数据透传,两侧均输出 OpenTelemetry。
6. **降级**:Bun 不可用时,Rust 核心照常运行;outbox 积压,恢复后继续消费,并按时效丢弃过期的自动回复任务。

**Redis 使用约定**:Redis 不是事实来源,其中数据丢失后必须能从 PostgreSQL 重建或自然过期,不得存放消息、seq、outbox、审计、审批状态;key 以 `core:` 与 `ai:` 前缀分属两侧并配置各自 ACL;除明确声明的计数结构外,每个 key 必须带 TTL。详见第 37 章。

## 25. Rust 核心详细设计

### 25.1 模块与 crate 划分

| crate          | 职责                                            |
| -------------- | ----------------------------------------------- |
| `gateway`      | WebSocket 接入、鉴权、心跳、连接管理、限流      |
| `chat`         | 会话、成员、seq 分配、消息写入、撤回、已读      |
| `presence`     | 在线、输入中、多端状态                          |
| `fanout`       | 在线推送、跨节点广播、大群分片扇出              |
| `push`         | 离线推送(APNs / FCM / 厂商通道)、设备令牌、重试 |
| `internal-api` | gRPC 内部接口,供 Bun 调用                       |
| `store`        | 存储接口与 PostgreSQL 实现(sqlx)                |
| `common`       | 错误模型、鉴权、tracing、配置、proto 生成代码   |

技术栈:tokio + axum + tonic + tokio-tungstenite + sqlx,统一用 `tracing` 输出结构化日志与 OpenTelemetry。

### 25.2 消息写入事务(核心路径)

一次发送只做一个事务,保证不丢、不乱序、可重试:

1. 幂等检查:以 `(sender_id, client_msg_id)` 唯一键去重,重复请求直接返回已有结果。
2. 分配 seq:对会话行 `UPDATE conversation SET last_seq = last_seq + 1 WHERE id = $1 RETURNING last_seq`,行锁天然保证同会话串行且不回退。
3. 写入消息行,同时写入 outbox 事件(`message.created`)。
4. 提交后,进程内推送给在线连接,并通过 `Redis Pub/Sub` 通知其他节点。
5. 返回 ack(含 msg\_id、seq、服务端时间)。

要点:

- 热点会话的行锁是瓶颈,但单会话消息速率有限;超大群另行优化(见 25.4)。
- 客户端按 seq 补洞:发现断档时调用 `PullMessages(conv_id, from_seq)`。
- 撤回、编辑作为新的事件记录,不直接覆盖原文,便于审计。

### 25.3 连接网关

- 无状态:连接信息只在本节点内存,在线路由与跨节点广播使用 Redis(路由 key 带 TTL 并随心跳续期,广播走 Pub/Sub)。
- 协议:二进制帧(protobuf),首帧鉴权,心跳 30 秒,服务端空闲超时断开。
- 多端:同一用户多连接,按设备维度维护已读与同步位点。
- 背压:每连接发送队列有上限,超限断开并让客户端重连补洞,避免拖垮节点。
- 限流:按用户、IP、会话三层令牌桶,AI 主体与人类主体分别配置。

### 25.4 扇出与大群

- **小群(< 500 人)**:写时在进程内遍历在线成员直推,离线成员走推送。
- **大群**:消息只写一份(读扩散),在线成员按分片(成员 id 哈希)并行推送;离线推送进入批量任务。
- **超大群(万人级)**:引入专用扇出节点或外部队列,是 NATS/Kafka 的第一个触发场景。
- 群内 AI 事件(如多分身并发响应)通过 outbox 异步处理,不阻塞扇出。

### 25.5 内部 gRPC 接口

| 接口            | 用途                                              |
| --------------- | ------------------------------------------------- |
| `SendMessage`   | 以人或分身身份发消息,含 `on_behalf_of`、`ai_meta` |
| `RecallMessage` | 撤回(主人撤回分身消息或自己的消息)                |
| `GetContext`    | 拉取会话最近 N 条消息与成员信息,供 Agent 使用     |
| `GetPresence`   | 查询主人是否在线、是否正在输入,用于让位           |
| `PushCard`      | 向用户推送确认卡片、草稿卡片(特殊消息类型)        |
| `FreezeAvatar`  | 紧急冻结分身(账号疑似被盗时)                      |

所有接口使用服务间 mTLS 或签名令牌鉴权,并记录调用方与 `trace_id`。

### 25.6 可靠性

- 写入失败不产生半条数据:事务保证消息与 outbox 同生同灭。
- 进程崩溃:连接由客户端重连,服务端无需恢复内存状态。
- 推送失败:指数退避重试,令牌失效自动清理。
- 热升级:先摘除流量、等待连接排空,再重启;客户端自动重连补洞。

## 26. PostgreSQL 数据设计

### 26.1 分区与索引

- `message` 按时间分区(月),再按 `conv_id` 建组合索引 `(conv_id, seq)`;冷分区可归档到对象存储。
- `outbox` 按时间分区,消费完成后定期删除旧分区,避免表膨胀。
- 大表使用 `BRIN` 索引辅助时间范围扫描;向量表使用 HNSW 索引,并带 `avatar_id` 前缀过滤。

### 26.2 核心表(节选)

```
-- 归 Rust 所有
conversation(id, type, last_seq, settings jsonb, created_at)
member(conv_id, principal_id, role, joined_at, last_read_seq)
message(msg_id, conv_id, seq, sender_id, sender_type, on_behalf_of,
        content jsonb, schema_version, mentions, reply_to, ai_meta jsonb,
        client_msg_id, created_at)   -- UNIQUE(conv_id, seq), UNIQUE(sender_id, client_msg_id)
outbox(id, topic, key, payload jsonb, trace_id, created_at,
       locked_at, locked_by, attempts, done_at)
device(user_id, device_id, platform, push_token, updated_at)

-- 归 Bun 所有
avatar(id, owner_id, persona, model_profile, status, version)
policy(id, owner_id, scope_type, scope_id, rule jsonb, priority, version, enabled)
capability(id, name, schema jsonb, risk_level, provider, version)
capability_grant(avatar_id, capability_id, constraints jsonb)
agent_task(id, avatar_id, trigger_ref, status, plan jsonb, cost, trace_id, ...)

memory_item(id, avatar_id, scope, type, content, embedding vector,
            sensitivity, confidence, ttl, source_msg)
feedback(msg_id, actor, type, diff, reason, created_at)
```

### 26.3 outbox 消费约定

- 取任务:`SELECT ... FOR UPDATE SKIP LOCKED LIMIT n`,处理成功标记 `done_at`。
- 去重:业务层以 `(msg_id, avatar_id)` 唯一键保证幂等,重复消费无副作用。
- 失败:`attempts` 递增并退避重试,超过上限进入死信表并告警。
- 顺序:同一会话的事件按 seq 顺序处理;多个 Worker 间以会话为粒度加咨询锁。
- 时效:自动回复类任务带过期时间,积压恢复后过期任务直接丢弃。

### 26.4 权限与隔离

- PG 角色:`core_rw`(Rust)、`ai_rw`(Bun)、`readonly`(分析);`ai_rw` 对消息表仅 `SELECT`。
- 行级安全:所有表带 `tenant_id`,启用 RLS,为多租户预留。
- 敏感列(令牌、凭证)使用应用层加密(AES-GCM),主密钥由部署环境注入,支持轮换。
- 审计表只追加,并通过哈希链防篡改。

### 26.5 容量与扩展路径

- 起步:单主 + 流复制只读副本,读多写少的查询走副本。
- 增长:消息表继续按时间分区;热点会话缓存最近消息;搜索走独立副本。
- 瓶颈信号:主库写入 IOPS 持续高位 → 消息热数据迁 ScyllaDB(接口已隔离);连接数过多 → 引入 PgBouncer。

## 27. Bun AI 平台详细设计

### 27.1 模块划分

| 模块            | 职责                                                              |
| --------------- | ----------------------------------------------------------------- |
| `outbox-worker` | 消费 outbox 事件,分发到各处理器                                   |
| `router`        | 判断一条消息涉及哪些分身(被 @、主人为自动档、私聊对象)            |
| `policy`        | 策略合并与求值(会话 > 联系人 > 场景 > 日程 > 全局),条件插件注册表 |
| `classifier`    | 意图分类与是否需要回应的快速判断(规则 + 小模型)                   |
| `agent-runtime` | 上下文装配、规划、工具循环、护栏、结果生成                        |
| `model-gateway` | 多模型适配、路由、重试、降级、缓存、预算与计费                    |
| `tool-gateway`  | MCP 客户端、能力注册与授权、参数校验、沙箱调用                    |
| `memory`        | 记忆写入、检索、治理、风格画像                                    |
| `approval`      | L2 确认卡片、超时与升级                                           |
| `scheduler`     | 定时与主动任务(日报、提醒、跟进)                                  |
| `admin-api`     | 控制台接口、策略编辑、能力市场、用量与账单                        |

技术栈:Bun + Hono(或 Elysia)、Zod 做运行时校验、`Bun.sql` 访问 PG、connect-es 调用 Rust 内部接口、官方 MCP SDK 对接工具。

### 27.2 并发与进程模型

Bun 是单线程事件循环,需主动规避阻塞:

- **角色拆分**:同一二进制通过 `--role=worker|admin|scheduler` 启动不同角色,按需独立扩容。
- **CPU 密集任务**(WASM 插件、大文本处理、向量计算)放入 Bun Worker 线程池,主线程只做 I/O。
- **并发控制**:每个分身同时最多 N 个任务,全局按模型供应商设信号量,防止被限流。
- **多实例**:Worker 以会话为粒度加咨询锁,保证同一会话的事件有序处理。

### 27.3 事件处理流水线

1. `outbox-worker` 取到 `message.created`,先做廉价过滤(系统消息、已被处理、过期)。
2. `router` 找出候选分身,按 `(msg_id, avatar_id)` 去重建立 `agent_task`。
3. `policy` 求值:档位、时间、范围、频率、让位状态(调用 `GetPresence`)。
4. `classifier` 判断是否需要响应;不需要则记录「已评估、未响应」后结束。
5. `agent-runtime` 装配上下文(`GetContext`、记忆、风格、知识源)并规划。
6. 工具调用经 `tool-gateway`:权限与风险检查 → 参数校验 → 执行 → 审计。
7. 风险为 L2 时,创建 `approval` 并推送确认卡片,任务挂起;批准事件唤醒继续。
8. 输出经护栏(隐私、注入残留、人设一致性)后调用 `SendMessage` 发出,写审计与反馈钩子。

每一步输出结构化结果(决策、理由、置信度、耗时、token),写入 `task_step`,支持回放。

### 27.4 Agent 运行时

- **提示词分层**:系统规则 → 人设 → 风格 → 策略约束 → 记忆 → 会话上下文 → 工具定义,各层独立版本化与灰度。
- **不可信数据隔离**:他人消息放入明确标记的数据块,模型被告知其中的指令一律无效;指令来源只有主人配置与主人本人消息。
- **规划模式**:简单回复单步完成;复杂任务生成计划并逐步执行,支持中途向主人提问。
- **不确定即转人**:置信度低、情绪激烈、涉及金额与法律、涉及隐私时,生成「转交卡片」交给主人。
- **成本控制**:先走规则与小模型过滤;命中缓存直接复用;按分身日预算,超额自动降为手动档并提示。

### 27.5 工具网关与插件

- **能力注册**:每个能力声明名称、Schema、风险等级、所需授权、是否幂等、是否可回滚、成本估计。
- **执行前检查**:分身是否被授予、策略是否允许、风险是否需确认、参数 Zod 校验、频率限制。
- **授权**:用户通过 OAuth 授权第三方服务,令牌加密存库,执行时仅取短期、最小范围令牌。
- **插件**:轻量逻辑编译为 WASM,在受限运行时执行(无网络、限制内存与时间);需要联网或文件的工具走独立 MCP 服务;高风险代码执行放入容器级沙箱。
- **动态风险**:同一能力按对象、金额、频率、对话对象信任度动态升降级。

### 27.6 记忆服务

- **写入**:对话结束或任务完成后异步抽取事实、偏好、承诺,附来源、敏感级别、置信度、过期时间。
- **检索**:向量检索 + 关键词 + 时间衰减,必须带 `avatar_id` 与「对话对象可见性」过滤。
- **治理**:主人可查看、编辑、删除、一键遗忘;敏感类别默认不用于对外对话。
- **风格画像**:定期从主人历史消息提炼语气、长度、口头禅与表情习惯,并结合反馈更新。
- **反馈闭环**:采纳、修改、撤回事件(`feedback.submitted`)进入偏好库与评测集。

### 27.7 审批、定时与主动任务

- **审批**:确认卡片含操作摘要、影响范围、过期时间;批准、修改后批准、拒绝三种结果;超时默认拒绝并通知。
- **定时**:`scheduler` 以 PG 任务表 + 定时扫描驱动(可用 pg-boss / graphile-worker 或自实现),支持日报、提醒、承诺跟进。
- **外部触发**:日历、邮件、Webhook 事件通过适配器转为内部事件,与消息事件走同一流水线。

### 27.8 模型网关

- 统一接口封装多家 LLM,按任务类型路由(分类用小模型,规划与生成用大模型)。
- 重试、超时、熔断、供应商降级;语义缓存与提示词缓存。
- 按租户、分身、任务记账,支持预算上限与告警。
- 提示词、模型版本与路由规则作为配置资产,支持灰度与一键回滚。

## 28. 内部接口与事件契约

### 28.1 事件(outbox topic)

| 事件                                       | 产生方     | 主要消费方               |
| ------------------------------------------ | ---------- | ------------------------ |
| `message.created`                          | Rust       | router、memory、搜索索引 |
| `message.recalled`                         | Rust       | memory(撤销引用)、审计   |
| `member.changed`                           | Rust       | router(分身成员关系)     |
| `presence.changed`                         | Rust       | policy(让位判断)         |
| `policy.changed`                           | Bun        | 各节点缓存失效           |
| `task.step` / `task.completed`             | Bun        | 审计、客户端进度卡片     |
| `approval.requested` / `approval.resolved` | Bun        | push、agent-runtime      |
| `feedback.submitted`                       | Rust / Bun | memory、评测             |

所有事件带 `event_id`、`schema_version`、`trace_id`、`occurred_at`;消费端必须幂等。

### 28.2 proto 示例(节选)

```
message Principal { string id = 1; PrincipalType type = 2; }

message SendMessageRequest {
  string client_msg_id = 1;   // 幂等键
  string conv_id = 2;
  Principal sender = 3;
  string on_behalf_of = 4;    // 分身代发时为主人 id
  Content content = 5;        // type + payload + schema_version
  repeated string mentions = 6;
  string reply_to = 7;
  AiMeta ai_meta = 8;         // task_id、mode、tools_used、risk、confidence、hop_count
  map<string, string> ext = 15;
}

message SendMessageResponse { string msg_id = 1; int64 seq = 2; int64 server_time = 3; }
```

- 字段只加不改,废弃字段保留编号;枚举保留 `UNKNOWN = 0`。
- 客户端与服务端按 `schema_version` 协商,不认识的内容类型降级为文本。
- `hop_count` 在 `SendMessage` 处强校验:AI 对 AI 连续超过 N 轮直接拒绝并通知双方主人。

### 28.3 对外 API

- **客户端**:WebSocket(消息、同步、状态)+ HTTPS(登录、历史、控制台、设置)。
- **开放平台**:REST + Webhook(第三方 Bot、能力提供方、回调),签名与版本号约束,提供 TS 与 Rust SDK。

## 29. 关键流程

### 29.1 自动档:对方来消息,分身代为回复

1. 对方发消息 → Rust 事务写入消息 + outbox → 推送给在线成员并 ack。
2. Bun Worker 取到 `message.created` → router 找到主人 U 的分身 A(U 在该会话为自动档)。
3. policy 求值:档位、时间段、频率;调用 `GetPresence`,若 U 在线且正在输入则暂停。
4. classifier 判断需要回应 → agent-runtime 装配上下文与记忆 → 生成回复。
5. 护栏通过 → `SendMessage(sender=A, on_behalf_of=U, ai_meta=...)` → 客户端显示「AI 代发」。
6. 写审计与任务记录;U 可展开解释、撤回或纠正,纠正写入反馈与记忆。

### 29.2 手动档:被 @ 才响应

1. 消息含对分身的 @ → router 命中分身,policy 检查调用者是否有权调用该分身(主人本人或被授权对象)。
2. 通过后与 29.1 的 4\~6 步相同;未被 @ 的消息一律直接丢弃,不进入模型调用。
3. 他人 @ 你的分身:默认只允许低风险只读能力,写操作需主人事先授权或实时确认。

### 29.3 半自动档:生成草稿

1. 流程同自动档到生成回复为止,但不调用 `SendMessage`,而是 `PushCard(draft)` 推给主人。
2. 主人选择「直接发送 / 修改后发送 / 丢弃」;结果作为反馈事件进入偏好学习。
3. 草稿带过期时间,过期自动作废。

### 29.4 L2 高风险操作审批

1. 规划出需 L2 的步骤 → 创建 `approval`,任务状态置为 `waiting_approval`,推送确认卡片。
2. 主人批准、修改后批准或拒绝;超时默认拒绝并告知对方「需主人确认」。
3. `approval.resolved` 事件唤醒任务继续或终止;所有决策写入审计,包含批准人与设备。

### 29.5 接管与让位

- 主人输入或手动回复 → `presence.changed` / 消息事件 → policy 将该话题冷却 N 分钟。
- 主人点击「接管」→ 相关进行中任务全部取消(`handed_over`),分身停止并交出上下文摘要。
- 主人长时间无响应且对方多次追问 → 分身按策略发送「主人暂不在,已记录」类提示一次,不反复打扰。

### 29.6 AI 对 AI 与防循环

- 消息携带 `hop_count`,每经一次分身代发加一;超过上限由 `SendMessage` 拒绝并通知双方主人。
- 同会话同意图去重、限速;两个分身来回超过轮数时强制转人工旁观,由主人决定是否继续。

## 32. 可观测、测试与评测

**可观测**

- `trace_id` 贯穿 消息 → 事件 → 任务 → 工具调用 → 模型调用。
- 关键指标:消息投递延迟与 seq 断档数、outbox 积压与处理延迟、自动回复占比、采纳率、撤回率、转人工率、拦截数、模型延迟与成本。
- 告警:积压超阈值、失败率、预算超限、模型供应商异常、PG 复制延迟。

**测试**

- 单元与契约测试:proto 兼容、事件 schema、接口幂等。
- 集成测试:compose 环境下的消息 → 分身回复全链路,含崩溃重试。
- 压测:会话 seq 热点、连接数、大群扇出、outbox 消费吞吐,优先验证单写者与长连接内存。
- 混沌:杀 Bun、杀 Rust 节点、断 PG、模型超时,验证降级与恢复。

**AI 评测**

- 离线评测集:闲聊、任务、注入攻击、隐私泄露、情绪场景、多分身群聊;每次改提示词、模型、策略必须回归。
- 影子模式:新策略或新模型先旁路运行(只生成不发送),与主人实际回复对比后再放量。
- 红队:定期模拟社工攻击、越狱、AI 互聊死循环。
- 在线反馈:每条 AI 消息可「点赞 / 纠正 / 举报」,回流到记忆与评测集。

## 33. 扩容路径与触发信号

| 信号                           | 动作                                                                                                |
| ------------------------------ | --------------------------------------------------------------------------------------------------- |
| 主库写入 IOPS 持续高位         | 消息热数据迁 ScyllaDB(接口已隔离),PG 仅保留元数据                                                   |
| 连接数过多、PG 连接耗尽        | 引入 PgBouncer,核心与 AI 分池                                                                       |
| Redis 单实例吞吐或内存吃紧     | Redis 主从 + Cluster 分片,按用途(路由 / 限流 / 缓存)拆分实例                                        |
| outbox 积压、多消费者需求      | 先用 Redis Streams 做分发,仍不足再引入 NATS JetStream 或 Kafka,outbox 退化为「事务内写入 + 转发器」 |
| 万人群扇出延迟                 | 专用扇出节点 + 队列                                                                                 |
| 流程复杂、需长时间等待与可视化 | 引入 Temporal / Restate                                                                             |
| 历史搜索规模大                 | 引入 Meilisearch / OpenSearch                                                                       |
| 记忆向量量级过大               | 迁 Qdrant / Milvus                                                                                  |
| 模型成本与隐私压力             | 自托管小模型(vLLM)                                                                                  |
| 全球用户                       | 多区域接入点 + 区域化数据驻留                                                                       |

原则:**有信号才加组件**,每次引入都只替换接口背后的实现,不改业务代码。

## 37. Redis 使用设计

Redis 是**加速层而非事实来源**:丢失后必须能由 PostgreSQL 重建或自然过期,正确性只依赖 PostgreSQL 事务与唯一键。

### 37.1 用途与 key 约定

| 用途                   | 结构                 | key 示例                                                     | TTL                              | 归属 | 丢失后果                              |
| ---------------------- | -------------------- | ------------------------------------------------------------ | -------------------------------- | ---- | ------------------------------------- |
| 在线路由               | String / Hash        | `core:route:{user_id}` → node、conn、设备                    | 90 秒,心跳续期                   | Rust | 回退为向所有节点广播,客户端重连后重建 |
| 跨节点广播             | Pub/Sub              | `core:bus:node:{node_id}`                                    | 无(不持久)                       | Rust | 漏推由客户端按 seq 补洞               |
| 在线与输入状态         | String               | `core:presence:{user_id}`、`core:typing:{conv_id}:{user_id}` | 30 秒 / 5 秒                     | Rust | 短暂显示为离线                        |
| 近期消息与成员缓存     | List / Hash          | `core:recent:{conv_id}`、`core:members:{conv_id}`            | 10 分钟                          | Rust | 回源读 PG                             |
| 限流                   | 计数器 / 令牌桶(Lua) | `core:rl:{scope}:{id}`、`ai:rl:{avatar_id}`                  | 窗口长度                         | 双方 | 退化为本地限流                        |
| 登录令牌、一次性 nonce | String               | `core:auth:{token_id}`                                       | 按令牌有效期                     | Rust | 重新登录                              |
| 策略与分身配置缓存     | String(JSON + 版本)  | `ai:policy:{avatar_id}`                                      | 5 分钟,`policy.changed` 主动失效 | Bun  | 回源读 PG                             |
| 事件去重窗口           | String(SET NX EX)    | `ai:dedup:{msg_id}:{avatar_id}`                              | 10 分钟                          | Bun  | 以 PG 唯一键兜底                      |
| 让位冷却               | String               | `ai:cooldown:{conv_id}:{owner_id}`                           | N 分钟                           | Bun  | 默认保守静默                          |
| 并发信号量             | ZSet / 计数器        | `ai:sem:model:{provider}`、`ai:sem:avatar:{avatar_id}`       | 任务超时                         | Bun  | 退化为进程内信号量                    |
| LLM 语义 / 提示词缓存  | String               | `ai:llmcache:{hash}`                                         | 按内容类型                       | Bun  | 只是多花成本                          |
| 事件分发(可选)         | Streams              | `ai:stream:events`                                           | 按长度裁剪                       | Bun  | 转发器重放 PG outbox                  |

### 37.2 使用原则

1. **PG 是事实来源**:消息、seq、outbox、审计、审批状态、记忆一律不放 Redis。
2. **必带 TTL**:除限流计数器等明确声明的结构外,所有 key 必须设置过期;新增 key 类型需在本表登记。
3. **前缀与权限隔离**:`core:` 与 `ai:` 分属两侧,使用独立账号与 ACL;命令白名单,禁用 KEYS、FLUSHALL 等危险命令。
4. **锁的边界**:涉及正确性的互斥(会话事件顺序、seq)用 PG 事务与咨询锁;Redis 锁和计数只用于限流、去重、并发限制这类允许失误的场景。
5. **防大 key 与热 key**:单 key 体积与元素数设上限;近期消息缓存只存最近 N 条;热点会话读走进程内一级缓存。
6. **Cluster 友好**:同一会话相关 key 使用 hash tag(如 `{conv_id}`),保证落在同一槽。

### 37.3 部署与高可用

- **起步**:单主 + 1 个副本 + Sentinel 自动切换;AOF 每秒刷盘,辅以定期 RDB 快照;设置 maxmemory,淘汰策略用 volatile-lru(所有缓存类 key 均带 TTL)。
- **增长**:按用途拆成路由 / 限流实例(不允许被淘汰)与缓存实例(允许淘汰),避免缓存膨胀挤掉路由数据。
- **再增长**:Redis Cluster 分片,key 设计已满足 hash tag 要求。
- **客户端**:Rust 侧使用支持连接池、自动重连与 Pub/Sub 的成熟客户端;Bun 侧优先用内置 Redis 客户端,落地前验证 Pub/Sub、断线重连与 Cluster 行为,不满足再换 ioredis。

### 37.4 故障与降级

| 场景                     | 影响                       | 降级行为                                                                                                                        |
| ------------------------ | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Redis 不可用             | 路由、广播、缓存、限流失效 | Rust 退化为本节点内存路由 + 全节点广播,并以 PG 变更通知兜底;缓存直接读 PG,配合 singleflight 防击穿;限流改本地令牌桶(单节点近似) |
| Redis 不可用时的 AI 链路 | 去重、冷却、并发限制失效   | 去重靠 PG 唯一键;冷却缺失按保守静默处理;高风险自动操作暂停,聊天收发不受影响                                                     |
| Redis 重启或数据丢失     | 路由与缓存冷启动           | 客户端重连并通过心跳重建路由;缓存按需回源,启动期限制回源并发                                                                    |
| 网络分区                 | 节点间状态不一致           | 以 PG 为准;客户端靠 seq 补洞保证最终一致                                                                                        |
| 慢消费者订阅             | Pub/Sub 缓冲积压           | 设置输出缓冲上限,超限断开并重订阅                                                                                               |

### 37.5 监控

- 命中率、内存使用与碎片率、淘汰数、连接数、命令延迟分位、主从复制延迟、Pub/Sub 积压。
- 业务指标:路由查询未命中率、本地限流降级次数、缓存回源 QPS;任一异常升高触发告警。
